# Развёртывание удалённого API

Основной `docker-compose.yml` предназначен только для сервера. Он поднимает
два сервиса: PostgreSQL и удалённый API с миграциями Alembic. Chrome на
сервере не запускается: страницы Megamarket открывает браузер пользователя.

Интерфейс собирается при сборке образа и раздаётся пользователям — на их
машинах Node.js не нужен. Подробности в разделе «Раздача интерфейса».

База по-прежнему недоступна пользовательским компьютерам, но обеспечивает это
теперь не отдельная машина, а конфигурация:

- сервис `db` не публикует порт наружу вовсе — до него дотягиваются только
  сервисы этого Compose по внутренней сети;
- наружу опубликован единственный порт `8001` — сам API;
- веб-консоли к базе на сервере нет: смотреть данные можно через `psql` в
  контейнере, см. «Доступ к базе».

## Первый запуск

Получите проект:

```bash
git clone https://github.com/ordenmeny/cdp_parsing.git
cd cdp_parsing
```

Создайте серверный файл настроек:

```bash
cp .env.remote.example .env.remote
```

Заполните в `.env.remote` имя базы, пользователя, пароль и токен API.
`PARSER_DB_HOST=db` — это имя сервиса в сети Compose, менять его не нужно. Случайный токен можно создать командой:

```bash
openssl rand -hex 32
```

Имя базы, пользователь и пароль из этого файла не только используются
приложением, но и **создают** базу при первой инициализации тома `pgdata`.
Позднейшее изменение пароля в файле саму базу не переучит — менять его придётся
внутри PostgreSQL.

`.env.remote` хранится только на сервере и не попадает в Git. Такой же токен
передаётся разрешённым пользователям в их локальном `.env`, но реквизиты БД им
не передаются.

## Запуск одной командой

```bash
docker compose --env-file .env.remote up -d --build
```

Флаг `--env-file` обязателен: из этого файла Compose берёт значения для
инициализации PostgreSQL. Без него запуск прерывается с
сообщением вида `required variable ... is missing a value` — это защита от
старта с пустыми реквизитами, а не ошибка конфигурации.

Порядок такой: сначала поднимается `db`, Compose ждёт его готовности по
`pg_isready`, затем контейнер API выполняет

```text
alembic upgrade head
```

и только после успешной миграции запускает FastAPI на порту `8001`.

Проверка:

```bash
docker compose --env-file .env.remote ps
```

```bash
docker compose --env-file .env.remote logs -f remote-api
```

## Перенос данных со старого сервера

База на старом сервере (`10.0.0.198`) работает не в контейнере, а на хосте,
поэтому снимок делается обычным `pg_dump`. Порядок важен: восстанавливать нужно
**до** первого запуска API, иначе Alembic создаст пустую схему и восстановление
придётся накладывать поверх неё.

Сначала проверьте версию источника — образ в Compose не должен быть старше:

```bash
psql -h 10.0.0.198 -U <пользователь> -d <название базы> -c "SHOW server_version"
```

Снимите дамп в собственном формате:

```bash
pg_dump -h 10.0.0.198 -U <пользователь> -d <название базы> -Fc -f megamarket_sellers.dump
```

Поднимите на новом сервере только базу:

```bash
docker compose --env-file .env.remote up -d db
```

Восстановите дамп в контейнер:

```bash
docker compose --env-file .env.remote exec -T db pg_restore -U <пользователь> -d <название базы> --clean --if-exists < megamarket_sellers.dump
```

Убедитесь, что продавцы на месте:

```bash
docker compose --env-file .env.remote exec db psql -U <пользователь> -d <название базы> -c "SELECT count(*) FROM sellers"
```

Только после этого поднимайте остальное:

```bash
docker compose --env-file .env.remote up -d --build
```

Alembic увидит таблицу `alembic_version` из дампа и применит лишь те миграции,
которых на старом сервере не было.

Старую базу не удаляйте, пока новый сервер не отработает хотя бы один полный
цикл проверки продавцов.

## Подключение пользователей

API публикуется напрямую на порту `8001` внутри локальной сети. В `.env`
пользователя укажите внутренний IP-адрес или локальное DNS-имя сервера:

```dotenv
PARSER_REMOTE_API_URL=http://<внутренний-IP-сервера>:8001
```

Если на сервере включён firewall, разрешите входящие TCP-подключения к порту
`8001` только из пользовательской подсети. Порт PostgreSQL открывать не нужно —
он и не публикуется.

Маршруты находятся под `/api/v1` и требуют заголовок:

```text
Authorization: Bearer <PARSER_REMOTE_API_TOKEN>
```

## Раздача интерфейса

Собранный интерфейс появляется в образе на стадии `frontend-builder` из
`Dockerfile` и лежит в контейнере по пути `/app/frontend/dist`. Отдельно
собирать его не нужно, репозиторий собранных файлов не хранит.

Удалённое API публикует две ручки под тем же токеном:

```text
GET /api/v1/frontend         версия и размер архива
GET /api/v1/frontend/bundle  сам архив tar.gz
```

Версия — это sha256 от содержимого каталога сборки. Время изменения файлов в
неё не входит, поэтому пересборка образа без правок фронтенда не заставляет
пользователей скачивать архив заново.

Локальное приложение при запуске сверяет версию, при расхождении скачивает
архив и распаковывает его в свой каталог кэша
(`%LOCALAPPDATA%\MegamarketControl\frontend` на Windows). Страница остаётся
на `http://127.0.0.1:8000`, то есть браузер работает с одним источником и
запросы к API не становятся межсайтовыми.

Если сервер недоступен, приложение открывает ранее скачанный интерфейс, а при
его отсутствии пишет в лог ошибку и продолжает обслуживать API. Проверить
раздачу можно так:

```bash
curl -H "Authorization: Bearer $PARSER_REMOTE_API_TOKEN" \
  http://<внутренний-IP-сервера>:8001/api/v1/frontend
```

Ответ `503` означает, что в образе нет собранного интерфейса — соберите образ
заново командой `docker compose up -d --build`.

Настройки локального приложения (менять обычно не нужно):

```dotenv
PARSER_FRONTEND_CACHE_DIR=<каталог кэша интерфейса>
PARSER_FRONTEND_SYNC_TIMEOUT=15
```

## Доступ к базе

Порт PostgreSQL наружу не публикуется, поэтому подключаться нужно изнутри
контейнера:

```bash
docker compose --env-file .env.remote exec db psql -U serm -d megamarket_sellers
```

Разовый запрос без интерактивной сессии:

```bash
docker compose --env-file .env.remote exec db psql -U serm -d megamarket_sellers -c "SELECT status, count(*) FROM sellers GROUP BY status"
```

Если понадобится подключиться клиентом с рабочей машины, публиковать порт не
нужно — достаточно SSH-туннеля до сервера:

```bash
ssh -L 5432:127.0.0.1:5432 <пользователь>@10.0.4.69
```

Туннель сработает только вместе с временной публикацией порта у сервиса `db`
(`127.0.0.1:5432:5432`). Постоянно её держать не стоит: закрытый порт — часть
того, почему база недоступна пользовательским компьютерам.

## Обновление

```bash
git pull
```

```bash
docker compose --env-file .env.remote up -d --build
```

Сервер обновляйте раньше пользователей. После `git pull` у пользователя не
остаётся собранного интерфейса в репозитории — он приходит с сервера, поэтому
на момент их обновления ручка `/api/v1/frontend` уже должна отвечать.

## Остановка

```bash
docker compose --env-file .env.remote down
```

**Никогда не добавляйте `--volumes`.** Раньше данные продавцов лежали во
внешней PostgreSQL, и флаг стирал только временные файлы заданий. Теперь база
живёт в томе `pgdata` этого же Compose, и `--volumes` удалит её вместе с
продавцами.

## Локальный Docker-контейнер пользователя

Он вынесен в отдельный файл и на сервере не запускается:

```bash
docker compose -f docker-compose.local.yml up -d --build
```

Обычному пользователю Docker не требуется: локальный запуск через `uv` и npm
описан в корневом `README.MD`.
